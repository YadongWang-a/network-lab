## Question

把原型「假引擎」（D2：`buildSequence` L645-725 + `waitMs` 本地定时 + `animateNextHop`）换成真 `SimulationEngine` 驱动的最小可转发竖切：一台 PC ping 另一台 PC（含 switch 学习洪泛 + ARP + ICMP），以及跨路由器路径（消费 WF-7 自动路由表）。为后续协议铺开定骨架。

## Notes

- **处理器移植范围（最小集，全部来自 `src/legacy/processors/*.js`，改造为读 store 状态/写引擎事件的纯逻辑）**：
  - switch：MAC 学习 + 未知单播洪泛 + 定向转发（消费 `macTable`，端口 = `Connection.toPort`）。
  - host：ARP 请求/应答 + 缓存（`arpTable`，expiresAt 语义进引擎 ephemeral）、ICMP echo 收发、IP 层发送前查默认网关。
  - router：查 `routingTable`（WF-7 已自动写入）最长前缀匹配，直连（nextHop `0.0.0.0`）ARP 出网段，远端转 next-hop；TTL 递减/丢弃（time-exceeded 报文可留 WF-17 与 traceroute 一起做）。
  - kernel：把 legacy `packets_lib` 报文模型映射到 WF-2 判别联合 `Packet`（layers 层栈 + xid），事件经 `SimulationEngine.enqueue`/`step` 出队。
- **播放键改轨**：原型 start/step/pause/reset（L940-954）从 `runLoop` 假序列改驱动 `SimulationEngine.step()` 节奏（参考骨架注释：暂停/单步由 controller 控制调用节奏）；trace 行/报文详情数据改由引擎事件经 `simEventToViz`（WF-5 已定）生成，替代 `traceData`/`tracePackets`/`buildSequence` 的 append 路径。
- **时序现实化**：引擎驱动后动画节拍与报文时间戳真实（参考 50ms 空转循环做节流），xid/pending 表（骨架已有）供请求-应答关联。
- **验收门**：真实 store 拓扑（两 PC 共交换机）Ping 端到端产出 ARP 请求/应答 → ICMP echo/reply 完整序列并可单步；含两路由器三交换机拓扑先拉线（自动路由）再 ping 跨网段即通；trace 行点击重播（replayHop）保持可用或明确定义降级；9 个演示命令中 ping/traceroute 之外仍走假数据不回归。
- 单测契约（ARP 学习、查表、TTL）按 WF-12 定案形态落地到本票实现中（若 WF-12 未决则以 Bun 直跑断言为准，对齐 WF-6/7 验证模式）。

## Resolution（2026-09-07）

**已实现，验收通过（Bun 直跑断言 + 浏览器实测）。**

- **引擎落地 `src/engine/SimulationEngine.ts`（骨架重写为全功能）**：队列每元素 = 一条物理跳；
  处理器移植 legacy 四件并改纯逻辑——switchProc（源 MAC 学习 → `macTable`，广播/未知单播洪泛
  structuredClone 拷贝、按表定向转发，跳事件带 `delivered` 区分洪泛拷贝）、hostProc+kernelProc
  （ARP 学习/应答、ICMP echo 应答、echo-reply/time-exceeded 按 xid 唤醒 pending）、routerProc
  （TTL 递减、归零发 ICMP time-exceeded、`lookupRoute` 最长前缀匹配消费 WF-7 `routingTable`、
  ARP next-hop 后重写 L2 转发）。本机发送 `sendFrom` 双轨：路由器查表 / 终端直连网段直发 +
  默认网关。引擎对宿主只依赖 `EngineCtx{getTopology,patchDevice}`（接 store），ephemeral 态
  （队列/pending/复位代数 gen）不进 store；ARP/MAC 老化只写 `expiresAt` 读取时判断。
  drop 即结算同 xid 等待者（无路由 ping 不再挂 20s 超时）。
- **公开 API**：`engine.ping(srcId, dstIp)` / `engine.traceroute(srcId, dstIp)`（先挂完成等待再发送，
  防回程先至丢 resolve）；`reset()` 代数守卫旧续延。
- **原型接线（WF-14 D2 数据流替换）**：ping/traceroute 播放键（start/step/pause/resume/reset）改驱动
  `engine.step()` 节奏；追踪行/报文详情/动画由引擎事件生成（`consumeEngineEvent`：首跳建行、仅
  delivered 跳更新 toId）；重播行无 toId（广播）时按邻居逐跳重放洪泛。其余 7 个演示命令保留
  mock（buildSequence ping/traceroute 分支已删）。
- **单测契约**：`scripts/verify-engine.ts`（Bun 直跑断言，WF-12 定案前形态）——同网段 ping 全序列
  + ARP/MAC 学习 + 二次 ping 缓存命中、跨网段两路由器三交换机（r0.enp0s9 不连线 → WF-7 远端
  路由 next-hop 消费 + 回程非对称）+ TTL 递减 + 无路由 drop、traceroute（req,TE,req,reply 序列、
  TE 源 = 入接口 IP）。
- **i18n**：新增 sim.pickIncomplete/noIp/noGateway/noRoute/arpTimeout + gen.probe；gen.timeExceeded
  改为「TTL 耗尽，返回 Time Exceeded」（路由器推不出探测 TTL，「第 N 跳」口径交给探测行）。
- **顺带修复（M1 遗留）**：`onDropDevice` 同 handler 挂两层（外层 div + ReactFlow）冒泡触发两次，
  一次拖放双建设备——加 `stopPropagation`。
- **浏览器实测（headless CDP）**：种子拓扑 ping（4 行真实序列：ARP req/rep + ICMP req/rep，真实
  MAC）、单步逐跳推进且播完自动禁用、两路由器三交换机（r0.enp0s9 不连线）跨网段 ping 10 行
  完整序列（gw ARP → 转发 → r0 ARP next-hop 192.168.1.5 → r1 ARP pc8 → echo reply → 回程 r1
  直连 ARP pc0）、traceroute 逐跳 TE（TTL=1→r0、TTL=2→r1、TTL=3→echo reply）、行点击重播、
  TCP mock 命令不回归；`tsc --noEmit` / `eslint src` / `pnpm build` 绿。
- **备注**：曾观察到一次 ARP 三重应答——排查证实为自动化搭建时误接线（r1 两接口同接一交换机 →
  洪泛重复投递）所致，非引擎缺陷；正确拓扑下 Bun/浏览器均无复现。
