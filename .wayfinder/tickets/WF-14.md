## Question

制定重写顺序与里程碑，保证**中间版本始终可运行**；决定是否「双轨并行」（旧 vanilla 引擎与新版共存过渡）还是「整体切换」。这是统御性决策，影响其余 ticket 的执行次序。

## Notes

- 建议按依赖图推进：WF-2 → WF-3 → WF-1/6/7/10/11 → WF-4/5/9 → WF-8 → WF-12/13。
- 需明确每个里程碑的「可演示/可运行」验收点。

## Resolution（2026-09-03，经用户拍板两项决策）

**现状盘点（本票调研结论）**：运行中的应用 = `src/prototype/AppPrototype.tsx`（1316 行自包含 mock，UI 外壳即 WF-9 确认的设计系统）；legacy vanilla = `src/legacy/` 108 文件、**零 import 的死代码**；生产轨已备好但零 UI 接线：`store`（拓扑动作含 WF-6 分配 / WF-7 连线+路由重算）、`SimulationEngine`（骨架：事件队列/订阅/xid pending，**无处理器**）、domain 纯函数（ipam/routing/deviceFactory）、viz 色码注册表、i18n。原型只踩生产轨 4 个薄面：domain/types、domain/ipam（`SubnetPool` 内联副本）、visualization（`viz.colorOf`）、i18n。

### 决策 ① 迁移策略 = 绞杀者（strangler），不是双轨也不是整体切换

- **legacy vanilla 不搞双轨**：零引用死代码，作为算法参考源保留至 WF-18 清理。
- 运行中的「旧轨」实为原型自身的 mock 数据流；**UI 外壳整体保留**（WF-4/9 已确认的设计），逐条替换四条数据流：
  - D1 拓扑：原型 nodes/edges/拖放内联分配 → `store.topology`（addDevice/addConnection/removeDevice…）
  - D2 仿真：`buildSequence`+`waitMs` 假引擎 → `SimulationEngine` 真实事件 + `simEventToViz`（WF-5 已备）
  - D3 终端/租约/服务展示：占位 → 命令注册表（WF-11）+ 引擎/store 真数据
  - D4 持久化/测试/清理（WF-13/12/18）
- **连线语义 = 交换机终端**（用户拍板）：设备接口只能连交换机，画布 onConnect 校验目标 kind=`switch`，违例报错进 i18n。与域模型 `Connection.toSwitchId`、`connectedSwitchId`、WF-7 网段路由图一致；任意直连留作未来域模型扩展，不在本轮。
- **可运行性纪律**：每个里程碑以浏览器实测演示命令为验收门；每张票独立可提交、可回退。

### 风险与遗留（进 fog 或下游票）

- **kind 缺口**：原型有 `apache2`/`annotation`/`dhcpserver` 等，域 `DeviceKind` 只有 pc/router/switch/dns-server/dhcp-server/dhcp-relay-agent。apache2 归并为「带 apache2 服务的 pc」或扩 kind，交 WF-17/WF-10 处理（ServiceName 已含 `apache2`）。
- **'—'/unconfigured 双标记**：原型用双标记字符串表示未配置 IP，store 真身是 `ip=null`——M1 起单事实源为 null，'—' 仅展示层文案。
- 性能/规模目标未定（引擎 UI 化需节流节奏，参考原型 50ms 空转循环），不阻塞。
- M1 动手前先读 WF-15 附的「接线面清单」（源自 AppPrototype 结构摸底，行号已核）。
